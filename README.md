# KPI dashboard (demo)

[![Smoke test](https://github.com/SaraBSalazar/KPI_dashboard_demo/actions/workflows/test.yml/badge.svg)](https://github.com/SaraBSalazar/KPI_dashboard_demo/actions/workflows/test.yml)

A Streamlit dashboard for tracking the work of a small analysis/consulting team: a
personal time log, a project tracker with turnaround metrics, a goals/ratings view for
longer-running initiatives, and a tools inventory — plus a static, read-only snapshot
exporter for sharing it with people who don't run Streamlit.

**This is a public demo build.** It's a copy of a real, private dashboard with every data
file replaced by invented placeholders — fake project tags, fake groups, fake hours and
dates. Nothing here is real. It exists so the dashboard itself (the code, the charts, the
UX choices) can be shared, cloned, and adapted without exposing anyone's actual business
data. See [Differences from the private version](#differences-from-the-private-version)
below for exactly what changed going from one to the other.

## Quick start

```powershell
pip install -r Dashboard/requirements.txt
cd Dashboard
streamlit run KPI_Report.py
```

Opens at `http://localhost:8501`, pre-loaded with a full fake calendar year of activity.
Every widget interaction reruns the script and re-reads any file whose modification time
changed, so editing a spreadsheet in Excel and clicking anything in the browser shows the
new numbers — no restart needed.

Full details on sharing it on a LAN, the `?readonly=true` view-only flag, and the static
snapshot exporter: [Dashboard/HOW_TO_RUN.md](Dashboard/HOW_TO_RUN.md).

### Regenerating the fake data

```powershell
python generate_demo_data.py
```

Rewrites everything under `Data/` from scratch (fixed random seed, so the output is the
same every run unless you edit the script). Read it before adapting this dashboard to
your own data — it doubles as a worked example of the exact shape (columns, sheet names,
JSON structure) `Dashboard/kpi_data.py` expects from each file.

### Starting fresh with your own data

To actually use this for real tracking instead of the fake year, clear the placeholder
content first:

```powershell
python generate_demo_data.py --empty
```

This writes every file with the right columns/sheets but **zero rows** — a real blank
starting point for the current calendar year, not more fake content. It also removes the
few files that have no meaningful "empty" state of their own (`special_project_tasks.json`,
`beyond_projects.json`, and their Excel mirrors): the dashboard recreates those correctly
the moment it needs them, either empty or via a small generic placeholder you can edit or
clear from the Special Projects page.

From there:

- Open the dashboard and use **Add Data** to add your first real project, or edit
  `Data/KPI_<year>.xlsx` / `Data/track_time.csv` directly in Excel.
- Delete `generate_demo_data.py` once you don't need it anymore, or keep it around as a
  reference for the exact file shapes the dashboard expects.
- If your reporting year doesn't run Jan–Dec, see
  [Differences from the private version](#differences-from-the-private-version) below for
  where that convention lives and how to change it.

## What's in here

| Output | Built by | What it's for |
| --- | --- | --- |
| **Live dashboard** | `streamlit run Dashboard/KPI_Report.py` | Day-to-day use. The only place data can be edited. |
| **Static snapshot** | `python Dashboard/export_snapshot.py` | One self-contained HTML file in `Share/` — browses like the dashboard (period selector, tabs, week/month/project pickers) but needs no server and nothing running. Read-only, frozen at export time. |

### Repository layout

```
Dashboard/              the Streamlit app, chart builders, and the snapshot exporter
Data/                   fake data, regenerated by generate_demo_data.py
generate_demo_data.py   writes every file under Data/ from invented placeholders
```

### Dashboard modules

| File | Role |
| --- | --- |
| [KPI_Report.py](Dashboard/KPI_Report.py) | Main page — Week / Month / Year tabs over the time log, plus the period selector and glossary every page inherits. |
| [kpi_data.py](Dashboard/kpi_data.py) | All file reading, period discovery, and shared computation. Deliberately **Streamlit-free** so the snapshot exporter can import it headless. |
| [kpi_cache.py](Dashboard/kpi_cache.py) | `st.cache_data` wrappers keyed on each source file's mtime — fast reruns, but any edit (from the app or from Excel) invalidates the key and reloads. |
| [kpi_charts.py](Dashboard/kpi_charts.py) | Plotly figure builders. Light/dark themes are module globals, so `set_theme()` re-themes everything that follows. |
| [kpi_style.py](Dashboard/kpi_style.py) | Shared visual identity — webfonts, metric cards, pill nav, page header helpers. Base theme tokens live in `.streamlit/config.toml`. |
| [export_snapshot.py](Dashboard/export_snapshot.py) | Builds the static HTML. Stores each chart once as a light+dark figure spec and draws it on demand, which is what keeps a page holding every view at once fast to open. |

### Pages

- **Week / Month / Year** (main page) — hours by project and major task, week-over-week
  change, category distribution, active projects, projects received vs finished, and the
  editable time-log table.
- **Projects Review** — year at a glance, needs attention, project turnaround, hours by
  project, complexity, project definition, who-we-work-with, consulting, non-quantifiable
  outputs, and "beyond projects" cards. Driven purely by the project tracker, so it works
  for a period that predates the time log.
- **Special Projects** — goal-rating bubble chart, per-project cards, task checklists with
  planned dates, and predicted timelines.
- **Add Data** — quick-add and edit forms for projects and consultation meetings.
- **Tools & AI Skills** — inventory of tools and automations built, with a breakdown by
  type, use, and project origin.

Appending `?readonly=true` to any page URL hides every editing control. It's a display
flag, **not** authentication — anyone can remove it from the URL.

## Data model

Reporting periods are plain **calendar years** (Jan 1 – Dec 31), auto-discovered from
sheet names inside every `Data/KPI*.xlsx`: a sheet named `2025_CALENDAR` (plus an optional
`2025_CALENDAR_meetings`) becomes the selectable period "2025". A new year just needs new
sheets — no code change. (The private original uses a different reporting-year convention
tied to its own institution's fiscal calendar — see the note below.)

| File | Holds |
| --- | --- |
| `Data/track_time.csv` | Personal time log, `;`-separated: entry, category, hours, major task, month, week, notes. Powers the Week/Month/Year views. |
| `Data/KPI_<year>.xlsx` | The project tracker — one `<year>_CALENDAR` sheet plus a `<year>_CALENDAR_meetings` sheet for consultations. |
| `Data/Special_Projects_Ratings.xlsx` | Longer-running initiatives and their goal ratings. |
| `Data/special_project_tasks.json` | Per-project task checklists (source of truth), mirrored to `Special_Projects_Tasks.xlsx` on every edit. |
| `Data/beyond_projects.json` | "Beyond projects" cards (source of truth), mirrored to `Beyond_Projects.xlsx` on every save. |
| `Data/custom_tags.json` | Remembers new dropdown options until they're used in a saved row. |
| `Data/tools.xlsx` | Tools/automations inventory. |
| `Data/project_pause_notes.json` | Per-pause notes and "forgive" flags on the turnaround chart (Projects Review) — a forgiven pause's days are excluded from that project's turnaround medians. |

The two JSON files are the dashboard's working copies because they hold shapes (a nested
to-do list, free-text cards) that don't map onto any existing spreadsheet column; the
Excel mirrors exist so everything stays readable outside the app.

## Differences from the private version

Everything below was changed going from the real, private dashboard to this public demo —
useful to know if you're comparing the two, or adapting this code back toward a real,
institution-specific setup:

- **All data is invented.** Every project tag, group name, date, hour, and rating in
  `Data/` comes from `generate_demo_data.py`, not from any real tracker. Project tags use
  deliberately different naming (`GEN_014`, `XX - general consulting`, ...) so nothing
  here can be mistaken for a real project.
- **Calendar-year periods instead of a fiscal year.** The private original runs reporting
  periods on its own institution's fiscal calendar; this demo uses plain Jan–Dec years
  instead, since there's no institutional date to anchor to here. That convention lives
  entirely in `discover_periods()` in `kpi_data.py` (and the one matching month-range
  calculation in `KPI_Report.py` / `export_snapshot.py`) — swap it for your own fiscal
  convention if you have one.
- **Generic naming throughout.** The main file is `KPI_Report.py` (not a person's name),
  page titles read "KPI Report", and file-glob patterns look for `KPI*.xlsx` instead of a
  name-prefixed pattern.
- **`publish_snapshot.ps1` takes parameters instead of hardcoded paths.** The private
  original hardcodes one person's Python install, Claude CLI path, and private artifact
  link as defaults so its scheduled task runs unmodified. This copy ships with no
  defaults for any of those — fill them in via command-line parameters (see the comment
  at the top of the script, and [HOW_TO_RUN.md](Dashboard/HOW_TO_RUN.md)) before using it.
